Nesta pasta você irá construir os fundamentos de um projeto "Pantonic*". O resultado serão dois documentos, um documento de governança, e outro documento de arquitetura reusável.
Vamos começar com a governança.
Uma aplicação "Pantonic*" possuem algumas premissas repetíveis:
- São aplicações majoritariamente desktop
- Utilizam o stack Python e Pyside6 como base, e uma arquitetura base MVVM (mais apropriada para aplicações desktop)
- São obcecadas pelas regras de clean arquitecture, clean code e melhores práticas
- Seguem um "core" reusável e comum, que corresponde à camada de infraestrutura
- São extensíveis baseada no conceito de plugins.
Vamos iniciar descrevendo o que deve conter no documento de governança:
- Todo projeto deverá adotar o mesmo core "pantonico", que será descrito no documento "arquitetura reusável".
- Todo projeto deverá se diversificar com base nas camadas inferiores: domínio e casos de uso. Assim, quanto mais baixo na clean architecture, mais especializadas são as classes, mas quanto mais "alto" nas camadas da clean architecture, mais similares são as aplicações entre si.
- Operações agenticas: um projeto pantonico usará um agente de planejamento, que usará o modelo mais poderoso (Fable ou Opus, a depender da disponibilidade); um agente de execução, que será o modelo de melhor custo benefício (Sonnet) e um agente de coleta, responsável pela execução de operações de search, grep, leitura de codebase, de documentos e prompts, com a finalidade de filtrar o que é pertinente para consumo no contexto dos agentes mais poderosos
- Fluxo de desenvolvimento: regra básica: todo procedimento mais complexo deverá invocar o agente de planejamento para criação de um checklist de tarefas atômicas e descritivo o suficiente para que o agente de execução não necessite aumentar contexto com buscar transversais a uma tarefa; com o checklist criado, será feito o arquivamento desses planejamento em um documento centralizado "diário de obras", que servirá também como um kanban adaptado. Vários planejamentos e tíquetes avulsos serão inseridos nesse diário, permitindo a imediata identificação do trabalho com seu status (backlog, in progress, in review, blocked, done e cancelled). Esse documento deverá possuir um índice abrangente que permita que o agente de execução encontre seu trabalho sem ler seções irrelevantes ao seu contexto; com relação à execução, toda tarefa ocorrerá dentro de um contexto limpo, nunca o agente deverá tentar desenvolver várias tarefas em um mesmo contexto. Ele sempre irá fazer o handover para o usuário limpar o contexto e invocar uma nova tarefa. Todo desenvolvimento seguirá o TDD, garantindo prioritariamente dois tipos de testes: funcionais (verifica se a função faz o que ela deve fazer) e de regressão (verifica se um estado funcional anterior não se quebrou, isto é, se não ocorreram colaterais.
- Fluxo de extensão: a extensão das capacidades de uma aplicação ocorrerão por meio de "plugins". Como se depreende do nome, e da clean architecture, plugins sempre serão incrementos funcionais atômicos, com proposito e operação específico, e não conflitantes com outros plugins. Via de regra, a criação de um novo plugin, ou melhor, a evolução da aplicação com uma nova funcionalidade, seguirá o fluxo de trabalho: criação de uma POC separada da aplicação, com a finalidade pretendida, estresse da POC até que o cliente valide o atendimento, uma vez validada, é iniciada a etapa de integração com a aplicação "Pantonic*", onde os agentes deverão dissecar a POC nas camadas da clean architecture, e inserção do código. Finalmente, o conjunto é testado.
- Deverão ser criadas guardrails para todos os agentes, para evidenciar a "obsessão pela clean architecture e clean code", impedindo violação de camadas e princípios.
- Fluxo de projeto: um projeto inicia-se com quatro artefatos: 
- - PRD: onde são coletados os objetivos da aplicação, determinado os casos de uso, elementos de domínio, requisitos, estruturas de dados e linguagem ubíqua necessários para a construção da camada de domínio e de casos de uso com base na clean architecture
- - Architecture: é criado o modelo conceitual da arquitetura com base no MVVM e clean architecture. Devem ser determinados os limites de cada camada, e inserção das responsabilidades de cada camada. Cada responsabilidade deverá ser mapeada aos casos de uso e requisitos coletados na etapa de PRD.
- - Spec: é especificadas as classes python que materializem as responsabilidades traçadas no documento de architecture. Nesta etapa, deverá ser proposto o filesystem, as assinaturas das classes, docstrings, e técnicas de projeto para garantir o desacoplamento tecnológico da aplicação, como inversão de dependência, strategy, unit of work, etc.
- - Sprint Plan: organiza o documento spec nos checklists a serem documentados no diário de obras, e adequado para handover de execução. Deverá ser organizado os checklists de modo que rapidamente os entregáveis sejam testáveis pelo usuário. No Sprint Plan também são definidos os testes funcionais, que irão validar a efetividade do desenvolvimento feito, assim como outros critérios.

Vamos falar agora sobre o segundo documento, a "arquitetura pantonica". Na pasta "D:\workspaces\PantonicVideo" está a aplicação que originou estes conhecimentos, seja de governança quanto de aplicação. Essa aplicação é um case de sucesso dessa arquitetura. O que o documento "arquitetura pantonica" deverá fazer é ler toda essa aplicação, e traduzir no modelo de infraestrutura a ser reusado por outras aplicações 'Pantonic*". Isto é, o PantonicVideo tem um core robusto e pouco alterado. Os plugins, por sua vez são especializados e não são reusáveis. O "arquitetura pantonica" deverá descrever como as demais arquiteturas deverão construir um core similar, principalmente no tocante ao Pyside6, operações de OS, IN/OUT e outras operações generalizadas, assim como os conceitos de camada de anti corrupção, serviços, etc.
